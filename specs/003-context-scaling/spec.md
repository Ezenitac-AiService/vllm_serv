# Feature Specification: 컨텍스트 윈도우 스케일링 벤치마크 (Context Scaling Benchmark)

**Feature Branch**: `003-context-scaling`

**Created**: 2026-07-10

**Status**: Draft

**Input**: User description: "e2b, e4b, 12b들을 8k 부터 1k씩 늘려가면서, 메모리 사용량과 답변을 시작할때까지 지연된 시간, 초당 토큰 생성 개수를 벤치 마크해서 보고서를 작성하는 벤치마크 코드. 여기서 정해야 할것은, 입력 컨텍스트 윈도우 크기를 언제까지 늘려야 하는가? oom인가, 아니면 현실적으로 사용할수 없는 토큰 생성 속도가 나올때인가"

## Clarifications

- **벤치마크 중단 조건**: 메모리 한계(OOM)가 발생하거나, 응답 대기 시간(TTFT)이 60초를 초과하여 현실적으로 사용 불가능한 속도가 측정될 경우(둘 중 먼저 도달하는 조건), 해당 모델의 벤치마크 루프를 종료하고 다음 모델로 넘어갑니다.
- **정확도 및 답변 품질 측정 방식**: Needle in a Haystack (건초더미 바늘 찾기) 검증 방식을 도입하여, 긴 문맥 텍스트 중간에 특정 핵심 사실(비밀번호 등)을 숨겨두고 모델이 이를 정확히 찾아내어 100% 답변하는지를 코드로 자동 검증합니다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 컨텍스트 길이에 따른 상세 성능 프로파일링

관리자는 E2B, E4B, 12B 세 가지 모델에 대해 입력 컨텍스트 윈도우를 8K부터 시작하여 1K씩 점진적으로 증가시키면서 성능 한계와 스케일링 특성을 파악할 수 있어야 합니다.

**Why this priority**: VRAM(메모리) 용량 한계(OOM)와 연산 병목에 따른 속도 저하(TTFT 폭증)라는 두 가지 현실적 제약 중, 어떤 모델이 어떤 컨텍스트 길이에서 한계에 도달하는지 정확한 수치적 근거를 확보하기 위함입니다.

**Acceptance Scenarios**:

1. **Given** E2B, E4B, 12B 모델 환경이 구성된 상태에서, **When** 벤치마크 스크립트를 실행하면, **Then** 각 모델별로 8K부터 1K씩 입력 길이가 증가하며 벤치마크가 순차적으로 수행됩니다.
2. **Given** 벤치마크가 진행되는 동안, **When** 각 측정 단계가 완료되면, **Then** 해당 구간에서의 피크 VRAM 사용량, 답변 시작 지연 시간(TTFT), 그리고 초당 토큰 생성 수(TPOT)가 측정되어 기록됩니다.
3. **Given** 스크립트 실행이 종료되면, **When** 결과 보고서를 확인하면, **Then** 각 모델이 어떤 한계(OOM 또는 실사용 불가 속도)에서 중단되었는지와 전체 데이터 스케일링 추이가 정리된 리포트를 볼 수 있습니다.

## Definition of Done (작업 종료 조건) *(mandatory)*

- **DoD-001**: 8K부터 1K씩 컨텍스트를 늘려가며 테스트하는 자동화된 벤치마크 스크립트 구현 완료
- **DoD-002**: 벤치마크 결과가 측정 항목(VRAM, TTFT, TPOT)별로 기록되고 최종 보고서 형태로 출력됨
- **DoD-003**: 명확한 종료 조건(OOM 발생 또는 특정 지연 시간 초과)에 도달하면 해당 모델의 테스트를 우아하게(gracefully) 중단하고 다음 모델로 넘어가는 로직 구현 완료

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 스크립트는 설정된 초기 길이(8K)부터 시작하여 1K씩 정확히 텍스트 길이를 증가시켜 프롬프트를 생성해야 합니다.
- **FR-002**: 각 테스트 구간마다 최대 VRAM 사용량을 정확히 측정하고 기록해야 합니다.
- **FR-003**: 첫 토큰이 생성되기까지 걸린 시간(Time To First Token, TTFT)을 분리하여 측정해야 합니다.
- **FR-004**: 프롬프트 처리가 끝난 직후부터 생성이 완료될 때까지의 초당 토큰 생성 수(TPOT)를 측정해야 합니다.
- **FR-005**: 벤치마크 실행 중 OOM(Out of Memory) 에러가 발생할 경우, 프로세스가 크래시되지 않고 실패 지점을 기록한 뒤 다음 모델 테스트로 넘어가야 합니다.
- **FR-006**: 벤치마크 수행 루프의 명확한 종료 조건 로직이 구현되어야 합니다.
- **FR-007**: 모델의 문맥 파악 능력을 정량적으로 평가하기 위해 'Needle in a Haystack' 테스트를 구현해야 합니다. 대량의 텍스트(배경 지식) 사이에 특정 식별 가능한 문장을 삽입하고, 모델이 해당 문장의 내용을 정확하게 추출해 내는지 자동 검증(Exact match 또는 Keyword match)하여 정확도(Accuracy) 지표를 기록해야 합니다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 세 가지 모델 모두 8K에서 시작하여 지정된 중단 조건(OOM 등)에 도달할 때까지 연속적으로 벤치마크가 수행되어야 합니다.
- **SC-002**: 수집된 데이터는 컨텍스트 길이에 따른 성능 저하(VRAM 증가, TTFT 증가)의 상관관계를 명확히 보여주는 데이터 형식(또는 표)으로 리포팅되어야 합니다.

## Assumptions

- 기존 벤치마크 시스템(LlamaManager 등)을 확장하여 TTFT를 정확히 측정할 수 있는 수단(스트리밍 등)을 도입할 수 있습니다.
- VRAM 모니터링은 기존과 동일하게 nvidia-smi 등 외부 도구를 서브프로세스로 활용합니다.
